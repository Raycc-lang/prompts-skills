# Personal review preparation and interpretation — 2026-09-09

Ray requested access to the four generated skills for personal reading/use, followed
by analysis of how to improve skill-authoring. The proposed shortening/formatting
idea was explicitly an example, not a requested rule.

## Prepared trial

`prepare_personal_review.py` copies each frozen pair wholesale into a private
Documents directory, initializes independent disposable state with each package's
own initializer, and checks source/copy hashes. It provides reading links, paired
job-review and web-research prompts, and feedback guidance. No maintenance files
outside the install units travel with the copies. No global installation or live
search is part of preparation. Human trial outcomes remain pending.

## What the available evidence establishes

The prior [report](report.md) records equal 37/37 targeted outcomes, one authored
artifact per condition, and a 64.1% smaller treatment installation. This measures
packaging separation, not shorter instructions: treatment job-search entrypoint
length increased from 850 to 986 words. Both retained the full decision prompt.
It does not establish general efficacy, equivalence on untested outcomes, or a
causal explanation for every difference between the two author runs.

Direct inspection today confirms identical searching-the-web entrypoints. Its
practical-routing reference changes a link label; tool-command references also
differ. These are four folders but not four independent inventions or replications.
Both authors preserved a pre-existing general web router. Job-search entrypoints
contain substantial source-policy summaries and both require the complete policy.

## Improvements worth investigating

1. **Measure the result Ray actually uses.** The earlier criteria exercise gate,
   recovery and state decisions well, but leave live search usefulness, readability,
   unnecessary interaction and some report-contract details unmeasured. Add Ray's
   concrete preferred/rejected outputs to subsequent test cases. This improves the
   evaluation evidence first; current evaluation.md already instructs measuring
   quality and friction, so another generic instruction would duplicate it.
2. **Investigate policy duplication only if it causes a problem.** Both entrypoints
   summarize a longer required policy. A short orientation plus precise loading
   cues might reduce maintenance drift, but repeated high-risk rules could also
   improve execution. This is an inspection-based hypothesis, not an observed
   failure. Compare a narrow candidate against the existing package on a real
   omission or contradiction before recommending a general compression rule.
3. **Test the authoring capability this task did not exercise.** Rich existing
   policy made preservation possible in both arms. A new-procedure or repair task
   with known successful/failed examples would better test whether the authoring
   skill recovers useful decisions. Repeated author pairs are needed to distinguish
   an effect from author variation. Do not keep tuning this source until one arm wins.
4. **Investigate exact report requirements separately from score totals.** The prior
   report observed that P paraphrased an application-disposition block while Q kept
   its form more consistently. If Ray considers that consequential, specify the
   expected output and compare actual answers on that requirement. The observation
   does not change the frozen 37-criterion result or prove an authoring mechanism.

## Runtime decision

Leave skill-authoring unchanged at this stage. It already requires useful packaging,
no target line count, comparable downstream evaluation, and separation of observed
benefit from untested claims. Adding “may not improve results but improves format
and reduces length” would assert an unestablished general benefit, contradict this
entrypoint-length observation, and repeat existing uncertainty guidance.

After Ray's trials, use each concrete complaint to locate the responsible layer:
host/setup, generated instruction/resource, inherited source policy, or missing
authoring decision. Repair the generated package where appropriate; change the
authoring skill only when its instructions plausibly explain the defect. Compare
the candidate repair on the failing input and a case that already worked. Personal
preference is valid design input, but should not be relabeled measured task accuracy.
