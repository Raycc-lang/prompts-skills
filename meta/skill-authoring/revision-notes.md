# 2026-09-06 — Teach decision extraction before packaging

## Request and rationale

Ray accepted the review's diagnosis and requested implementation, then asked us to
check the recent task "Expand reusable private agent skill". The authorized change
is to this authoring skill, its supporting reference/template, and maintenance
records. The private résumé workflow was inspected, not modified.

The old entrypoint specified packaging and maintenance in detail but left the
transition from evidence to useful decision instructions largely implicit. Its
acceptance criteria could establish that a task passed without establishing that
the skill helped. These are design-level findings; downstream failure frequency
has not been measured. FO2 tempers the diagnosis: the old skill can support useful
consolidation when a project already contains substantive knowledge and policies.

## Coordinated change

This is one coherent workflow revision, implemented across the entrypoint, anatomy,
template, worked example, and evaluation reference. Small additive patches would
retain the competing checklist-centered workflow.

| Previous behavior | Replacement and intended effect |
|---|---|
| Observe a run, then write the skeleton | Establish intended difference; recover decision cues, criteria, alternatives, boundaries, and checks before packaging |
| New authorship and consolidation share one path | Preserve existing knowledge/tools for migration; extract missing decisions for new procedures |
| Procedural form privileged over other content | Select useful instructions, examples, knowledge, scripts, and assets according to runner needs |
| Generic runtime-check and body-length prescriptions | Task-appropriate verification and no numerical writing target |
| Passing representative task can imply stability | Distinguish mechanical checks, actual behavior, and comparative evidence; no automatic stability after two runs |
| Prohibitions require observed model failure; other skill names forbidden | Guards can implement requirements or concrete risks; dependencies allowed with availability/fallback handling |
| Failed precondition stops the workflow | Recover, branch, or stop affected work according to the dependency |
| Per-rule provenance and repeated gate checks | Consequential rule-group provenance outside install unit, with evidence strength distinguished |

Kept: explicit scope, discriminating descriptions, labeled outcomes, useful failure
evidence, selective reference loading, traceable maintenance, and deprecation of
bad rules. Prior FO1 repair is preserved: no inline provenance or portability tags,
no invariant/prohibition section added merely to satisfy a template.

## Recent result: what survives the review

Inspected the installed entrypoint, strategy and claim-policy references, original
project instructions, maintenance/test reports, and task command outputs. The package
preserves real decision criteria and knowledge, handles requested modes, and addresses
relocation and export-check defects. The trace reports three scenario tests and shows
sample preflight success. These are meaningful results for the migration request.

Much of the decision content predates this consolidation. There is no controlled
comparison isolating the authoring skill's contribution or a fresh-session downstream
quality comparison. This limits attribution; it does not invalidate migration success.
The source task already acknowledges its untested office-rendering and routing scope.
The sample draft is available in task history but its recorded local fixture paths
were absent during this review. Keep future evaluation inputs/outputs reproducible.

The existing overall conclusion is therefore revised from "likely weak generated
skills" to "a plausible weakness in creating new decision content, with a concrete
successful consolidation and unmeasured comparative benefit." A strong model may
compensate for missing guidance, but this run does not establish that causal story.

## Rejected directions

- Do not add five mandatory decision headings to every generated skill. The questions
  help the author reason; the output should take the simplest useful form.
- Do not remove substantive facts or tools to meet a prose or length preference.
- Do not require novel capability gains to accept a successful migration.
- Do not rewrite the résumé result merely to make it illustrate the initial critique.
- Do not add a fresh-agent benchmark requirement that blocks user-requested drafting
  when the environment cannot execute it; disclose the unvalidated claim instead.
- Do not attribute synthetic examples to real users or runs.

# Revision — 2026-09-14 — decision boundaries rather than incident patches

Ray explicitly requested a structural refactor and self-application of the meta-skill's
principles. Source snapshot: dc32d0a0d7004beaff20d4dddfa7c2495762609c.
The previous entrypoint already contained cue/decision/reason/boundary/check questions;
this revision makes their connection to repair, placement, and testing operational.

The workflow is now: establish task and evidence → derive the decision and its home
→ encode the procedure → test both sides and revise the mechanism → deliver evidence.
A new warning first prompts inspection of the choice that caused the failure. Related
incidents sharing that choice are consolidated; missing conditions, knowledge, delivery,
and deterministic mechanics lead to different repairs. Raw incidents remain maintenance
evidence. Explicit user methods and requirements still justify guidance without a
preexisting failure.

Placement depends on lifetime, breadth across tasks, and enforcement needs. Recurrence
alone does not imply either a skill or project context. Runtime instructions retain
the relevant command or interpretation when tooling enforces a requirement.
Constraint admission asks what consequential gap remains, and applies equally to
positive and negative phrasing.

Preserved: useful domain knowledge and tools, consolidation as a valid goal, conditional
recovery, description boundaries, authorization continuity, and honest validation.
The worked example now shows consolidation of warnings and placement. Evaluation adds
contrast cases, removal comparisons, and the distinction between forced execution
and actual host selection. The skill applies those decisions to its own maintenance.

This is a coordinated refactor, not a claim that the prior skill always produced poor
results. The 2026-09-08 successful consolidation experiment remains counter-evidence to
that blanket interpretation. No historical result or rejected direction was erased.
